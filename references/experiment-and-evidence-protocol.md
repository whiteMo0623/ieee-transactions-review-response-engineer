# 精简实验与证据协议

## 1. 将所有推理集中到 response-plan.md

为当前意见建立“主张—疑虑—证据”链，并在同一文件记录相关论文位置、代码文件/行号、既往证据复用判定、实验设计、实际结果和结论边界。不要为这些内容再创建独立摘要、代码地图、证据摘要或证据账本。

机制辨析实验应区分与疑虑有关的候选解释；涉及经验性主张判断时先写判定规则，再看结果。参数量核算、确定性数值检查或公式/复杂度分析按其问题设置核验标准，不强制构造两个解释。允许支持原主张、部分支持并收缩边界、不支持并修改或撤回主张。

这些疑虑分析、候选解释和判定过程属于内部推理，不是最终回复的写作顺序。得到结果后，按意见类型选择开场及证据—解释顺序，再选择最少充分证据；不默认把结果结论放在首句。

## 2. 保持完整性与公平性

涉及性能比较时，以原论文或官方实现为依据确定完整正式方案，不为节省成本擅自缩减已确定的数据、模型或训练预算。各方法采用一致的数据版本、划分、预处理、评价实现、硬件类别和 checkpoint 选择规则；方法特性要求不同设置时，解释必要性并报告资源差异。确定性检查等不需要训练的任务不套用训练预算要求。

默认正式训练使用足够大的 epoch 上限及验证集早停，最终加载验证集最优权重；不得根据测试集早停。用户指定方案或不适用早停的任务除外。提前满足预设验证早停条件不属于擅自缩减 epoch。多 GPU 时每卡独立任务，不用 DataParallel/DDP 跨卡同步同一训练任务；远程长训练按预计完成时间检查，常规间隔不少于 5 分钟。

默认单随机种子，除非用户明确要求多种子。方案不得擅自追加种子或缩减用户已经确定的重复次数；执行并记录所定全部种子及适用的随机源。不得只保留成功或有利运行。

涉及性能比较时，纳入审稿人要求且适用的方法及回答当前问题必需的强基线；机制辨析需要时设置控制组。不机械重跑与当前疑虑无关的全部基线，不给基线不公平的预算或调参范围。

## 3. 严格判断是否复用

先完整读取包含所有审稿意见的 `review_comments`，根据当前意见的核心疑虑、论文主张、方法模块、数据集、指标和所需证据，筛出可能相关的意见编号。不要先遍历既往案件目录或代码树。

逐个检查候选意见是否已经建立案件。尚未处理的意见只记录关联和潜在共用点，不假定已有结果，也不继续搜索其项目文件。已经处理的意见先只读取对应的 `response-plan.md`；只有其中的证据可能直接复用时，才读取该方案明确引用的结果、配置和代码文件。

直接复用既有结果前，逐项核对研究问题、数据版本与划分、模型/代码 revision、训练预算、checkpoint 规则、对比方法、指标、种子、统计单位以及原始结果可访问性。

任一关键条件不一致时，只把旧结果作为背景。可以复用不变的数据、模型和训练框架，但当前意见新增的控制变量、数据、基线、指标和分析必须完整执行。

在 `response-plan.md` 中仅记录候选意见编号、处理状态、关联理由、复用内容和判定结论。若完整 `review_comments` 中没有相关意见，写明“未发现相关既往意见”并停止该步骤。

## 4. 使用紧凑实验目录

只保留下列内容：

- 新增实验代码；直接调用原项目入口时在方案中引用原路径，无需复制；
- 原框架确实需要的配置；
- 逐运行或逐种子的机器可读结果；
- 最终回复使用的汇总表和图，包括从已核验外部结果生成的必要图表。

不要求独立 manifest、命令账本、证据账本、成功日志或 raw/processed 的机械分层。正式命令、环境、数据版本、种子、开始/结束状态和结果来源写入 `response-plan.md`，或由单一机器可读结果记录。

失败日志放临时目录，修复后保留失败原因的简短文字记录即可。不要保留 `__pycache__`、冒烟测试输出、重复图、渲染缓存或未进入回复的探索性图表。

### 供轻量审计读取的现有方案字段

只在 `response-plan.md` 顶部 frontmatter 保存以下少量引用，不另建配置或证据账本：

```yaml
code_files: ["/absolute/project/train.py", "experiment/analyze.py"]
result_files: ["experiment/results.csv", "/absolute/previous-case/experiment/results.json"]
approved_artifacts: {}
```

数组/对象使用单行 JSON 语法；其余字段使用初始化脚本生成的扁平格式。文件路径可为绝对路径，或相对 `response-plan.md` 所在目录；不要相对执行审计命令的目录。`experiment_required: true` 时两组引用均须非空；`false` 时可为空，但使用既往机器可读结果仍应列出原路径。旧案件可在原方案中补填这几项，无需重新初始化。若代码使用 `python -m`、二进制或其他入口，列出实际入口文件，并在正文记录完整运行命令。

`result_files` 只列实际结果，不列配置文件；方案正文同时保留字段/行列与主张的证据映射。审计只检查可访问性、非空和 JSON/CSV/TSV 基本内容，其他支持格式只作扩展名与非空检查，不能证明测量已运行或数值正确。

用户明确要求默认禁止的额外产物时，例如 `approved_artifacts: {"notes": "用户要求保留分析笔记"}`，记录案件内具体相对路径及请求依据；目录例外覆盖其下文件，不允许用整个案件目录作为例外。该字段记录已有用户授权，不产生新授权。用户指定的最终 Word 及其相邻案件备份可位于案件目录内，不视为冗余副本；若放在默认禁止的子目录中，同时记录该目录的请求依据。不得为通过审计自行增加例外或伪造结果。

## 5. 统计与结论门槛

涉及统计推断时明确实验单位和统计单位；对相同测试样本的比较使用适当的配对分析，以训练重复为单位的不确定性保留逐种子值。按问题报告样本量、效应量、置信区间及适用的检验/多重比较校正；先核验独立性或分组依赖。单次训练不能估计跨种子方差，测试样本间不确定性也不能充当训练重复的不确定性。确定性计算和不涉及统计推断的核验不强制置信区间或显著性检验。

不要把 `p > 0.05` 解释为等价。若要主张无实质差异，预先规定等价界值并使用等价检验或置信区间。结果混合时按数据集、场景或强度限定结论，不用总体均值掩盖失败子组。

## 6. 在方案文件内建立紧凑证据映射

在 `response-plan.md` 的“实际结果与证据映射”中，用一张紧凑表记录：回复主张、实际数值、来源文件、字段/行列、生成代码、关联运行或种子。无需另建 JSON evidence ledger。

在该区先记录意见类型，按主文件规则形成开场候选：明确增补型先说明增补，主张判断型仅在证据可直接支撑时结论先行。结果支持的解释单独记录，不默认作为首句；随后建立证据映射。

成文后反向检查比较级、因果词、显著性词和范围词。无法绑定实际结果的语句删除、改写为解释，或明确标注为假设。统计不确定性和结论边界只有在会改变主结论解释时才进入最终回复，其余细节保留在方案或论文中。
