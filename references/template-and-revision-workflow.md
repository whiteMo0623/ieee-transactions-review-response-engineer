# 三段回复模板与正文同步

## 何时读取与使用

首次新建 response Word、增加 Reviewer/Comment 块或同步正文修改记录时读取本文件。默认资源为 `../assets/response-template.docx`。模板从用户提供的 `Response_to_Reviewers_minor.docx` 提取，保留版式和样式，已去除特定论文的题目、稿号、意见、回复、修改摘录和实验图片。它是结构与样式来源，不提供当前论文的事实证据。

用户提供的已有回复文件优先；仅在需要新建回复文件时复制模板到指定路径，不覆盖已有文件，不直接编辑 Skill 内的模板。复制完成后即可将该 Word 路径传给 `init_review_case.py --word-file`。案件初始化脚本本身不负责创建 Word。模板路径以 Skill 根目录解析，不依赖当前工作目录。

## 文档结构与占位符

封面保留标题、稿件编号、论文标题、致编辑与审稿人的开头和 `Summary of Revisions`。随后是 Reviewer → Comment → 三段内容。

| 占位符 | 填写规则 |
|---|---|
| `{{MANUSCRIPT_ID}}` | 实际稿件编号；尚未知时不编造 |
| `{{MANUSCRIPT_TITLE}}` | 当前论文完整标题 |
| `{{REVISION_SUMMARY}}` | 正文统一落实后汇总实际修改；回复阶段可清空内容、保留标题 |
| `{{REVIEWER_NUMBER}}` | 实际审稿人编号 |
| `{{COMMENT_NUMBER}}` | 当前审稿人的实际意见编号 |
| `{{ORIGINAL_COMMENT}}` | 审稿意见原文，不改写措辞或数学表达 |
| `{{AUTHOR_RESPONSE}}` | 当前意见的完整回复 |

`Changes in Manuscript` 不设置内容占位符，初始保留标题和空白。不要写“待补充”“我们将修改”或推测性的正文摘录。模板资产保留占位符；实际回复文件应替换已知字段，阶段性不需要的可选内容留空，可提交版本不得残留占位符。

增加同一审稿人的意见时复制完整 Comment 块及三个区域；增加审稿人时再复制 Reviewer 标题，使用真实编号。复制后保持定位唯一，不固定意见数量。既有文件中的 `General Comment` 视为原始意见区的变体；纯正面评价且无修改要求时不制造实验和正文改动，可简短致谢，并保留已有两段结构，或在三段模板中将修改区留空、在内部记录“不适用”。该例外仅适用于无实质问题的评价，不套用于技术意见。

## 保留的样式

单栏 US Letter（8.5 × 11 英寸）；上/下边距 0.7083 英寸，左/右边距 0.7875 英寸；页脚为居中 PAGE 页码域。普通回复正文 Times New Roman 11 pt、1.15 倍行距。封面标题与稿号 14 pt，论文标题 12 pt；Reviewer 标题 13 pt，Comment 标题 11.5 pt，保持原模板层级。

| 区域 | Word 段落样式 | 标题及边框颜色 | 底色 |
|---|---|---|---|
| Original Comment | `Original Comment Text` | `A94442` | `FBEEEE` |
| Author Response | `Author Response Text` | `1F5E95` | `EEF5FC` |
| Changes in Manuscript | `Manuscript Changes Text` | `3E7C59` | `EEF8F1` |

三区标签为 11 pt 加粗，内容为黑色；边框 1 pt，边框与文字间距 6 pt，段落左右缩进 7 pt。它们是带边框和底色的 Word 段落，不是文本框或表格。保留彩色结构标签，不把整份 Word 强制改成正文 11 pt；新增数据表仍遵循 Skill 的三线表规则。

原文件有“标签和正文在同一段落、用换行分隔”的结构，不能只按独立段落标题查找，也不要直接给整个段落赋 `.text` 而丢失标签格式。按 Reviewer + Comment + 样式/标签联合定位；`Author Response` 从标签后开始，到 `Changes in Manuscript` 之前结束；修改区到下一个 Comment/Reviewer 或文档末尾结束。沿文档 XML 顺序处理内容，包含段落间的表格和图片。只修改正文 run，保留标签与样式；长回复可用相同样式的连续段落，并检查边框连续性与跨页效果。

## 阶段一：先完成 Author Response

1. 核对原始意见，实际完成本条所需的实验、分析或证明。
2. 按最终提交口吻写回复。对内容已确定、等待合并落实的正文编辑可预写 `We have added ...`、`We have revised ...`；不得将此许可延伸到未完成的实验、未得到的结果或未完成的证明。
3. 在 `response-plan.md` 的 Word 更新记录中注明回复状态、正文落实状态和修改记录同步状态。待落实项目写清“改什么、改在哪里、涉及哪些相关意见”，不另建修改账本。回复完成但正文尚待修改时分别记为“已完成 / 待落实 / 待同步”；不需要改正文时注明理由并记为“不适用”。
4. 只写入目标 `Author Response`。`Original Comment` 保持原文；新建文件的 `Changes in Manuscript` 留空，已有文件的该区保留。本阶段不强制先完成论文编辑。
5. 使用已核验的章节名称描述位置；未确定的新页码、行号、图表/公式编号留在内部待核验项中，不填入对外回复。正式结果和实质性解释仍必须可追溯。

回复阶段完成与正文落实分别报告；不要将完成时态的草稿陈述当作正文已经修改的证据。

## 阶段二：正文落实后填写 Changes in Manuscript

触发条件为用户要求“修改正文”“根据已完成回复统一修稿”“补充 Changes in Manuscript”或同义请求。若用户只要求填写修改区，先读取已修订的 LaTeX/PDF 核验，不擅自扩大为论文编辑。若尚无对应修改，只更新内部待落实记录，不伪造摘录。

1. 对涉及的相关案件合并重叠要求；同一处正文改动可对应多个意见，不重复添加相同内容，也不遗漏各条意见独有的要求。
2. 在授权范围内完成正文修改，或核验用户已完成的修改；依据当前修订稿确认章节、页码、行号及图表/公式编号。
3. 填写本条 `Changes in Manuscript`：先给出加粗的真实位置，再引用实际修改后的文字；引用正文沿用源模板的斜体样式，数学表达仍按 Skill 保留 TeX。只在需要时插入实际修订稿的图表，不从其他意见回复截图。
4. 同步 `Author Response` 中受正文最终改动影响的事实、范围和定位；若合并过程中改变了原定修改，相应修正回复。其他无关文字和原始意见保持原样。
5. 核对回复所述修改、实际正文和修改摘录三者一致，更新内部状态；全部相关项目完成、无遗留占位符或不一致后才记为“可提交”。

同一修改可在多个相关意见的修改区分别引用，使每条自包含；其他审稿意见编号及合并过程只保留在内部方案中。只有用户要求汇总修稿时才跨案件处理，不在单条回复任务中自动批量改写。

## 写入与验收

两个阶段均按 `response-and-artifact-protocol.md` 的局部编辑、备份、回读和视觉 QA 执行。阶段二的目标区域包括 `Changes in Manuscript` 及必须同步的回复句。已有 `<word-stem>.before-<comment-id>.docx` 经方案记录核验确属当前案件时继续保留、不覆盖；不能确认归属时才请求核实。staging 从当前 Word 创建，避免从旧备份恢复而丢失其他意见的新内容。

先在目标文件同目录 staging 中编辑、回读和渲染检查，再替换指定 Word。检查目标区域实际覆盖的全部页面以及必要相邻页；renderer 不支持页码筛选时可全文转换/渲染，只做目标页视觉检查。写回前确认目标 Word 未在编辑期间被其他操作更新。成功后清理本次 staging 与 QA 临时产物。

案件脚本的产物审计不判断两阶段的语义完成状态；方案中有明确待落实记录且修改区留空，是阶段一的合法结果，不应为通过审计而提前填入正文修改。
